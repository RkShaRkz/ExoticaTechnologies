# Completed Plan: plan-hullmod_exotic_installs_on_whole_ship-completed.txt

## Intent

The plan family started from a simple decoupling goal: `shouldShareEffectToOtherModules(...)`
was driving **two different concerns** at once — (1) *install extent* (which modules get the
exotic's hullmod installed) and (2) *effect sharing* (whether an exotic owned by one module
applies exotic-level effects to other modules). The intent was to introduce
`installsOnWholeShip()` as the single source of truth for concern #1, so a `HullmodExotic`
could install on ONE module while still sharing exotic-level effects with ALL modules.

In practice the "whole-ship install" half consumed the entire plan: anchoring whole-ship
writes on the correct ship, keeping identical-hull twins from bleeding into each other, and
making install/remove/OP-reset symmetric across every variant graph the game can read.
That second half is what this plan ultimately shipped.

## Scope

- `HullmodExotic.kt` — install/remove/destroy lifecycle, whole-ship anchoring, cleanup.
- `HullmodExoticHandler.kt` — install/remove flows, bookkeeping, work modes, gates.
- `FleetMemberUtils.kt` — root resolution, member/stats/variant identity helpers.
- `Extensions.kt` — `getWholeVariantGraph`, `shouldAllowInstallation`, refit predicates.
- `RefitButtonAdder.kt` — refit-root cache and display variant accessors (read/used, not edited

- `VariantTagProvider.kt`, `ShipModLoader.kt` — write-through and whole-ship mod reads.
- `AlphaSubcore.kt`, `DaemonCore.kt` — the two `installsOnWholeShip() = true` exotics.
- Test/results files and the planetside exoticatech + refit screens.

## Outcome

The feature works end-to-end and is validated:

- `installsOnWholeShip()` split shipped, with AlphaSubcore/DaemonCore opting into whole-ship.
- Whole-ship install reaches, and remove strips, every variant the game can read stats/costs
  from (`getWholeVariantGraph` = campaign + refit + display, id-gated to this ship).
- Cross-ship bleed between identical hulls is closed by a screen-aware, fail-closed
  `resolveWholeShipRootMember(member)` (named members always return themselves; child modules on
  the refit screen anchor on the stable refit-root id and must be carried by that root by
  variant-id string equality; planet-side never consults the refit cache).
- OP resets reliably across every module on uninstall. The mechanism that finally closed this is
  an `onPostDestroy` cleanup that is NOT from any revision: after the handler completes, it
  removes bookkeeping for both entering and resolved root member, finishes the uninstall
  sequence, then `clearHullmodLeftovers` scrubs the hullmod + stats listeners from the union of
  the callback variant's modules, the entering member's variant modules, and both whole graphs.
- Acceptance: `TEST_RESULTS22.txt` (refit + planetside ExoticaTech runs) passes — zero
  cross-ship mixed graphs, 250 listener removals, 12 anticipated `CHANGE-A` fail-closed paths,
  no OP reset failures, no flakiness.
- All diagnostic logging added during the work has been removed (commits f41a4c5, 830b265);
  the diagnostic emitters and `MIN_LOG_LEVEL = Level.WARN` gate the remaining lifecycle logs to
  ERROR-and-above only.

**Additions in HEAD that NO revision planned:**

1. **Named-member fast path** in `resolveWholeShipRootMember` — `if (!member.shipName.isNullOrEmpty()) return member`
   (FleetMemberUtils.kt:409-411). A ship root carrying a name is authoritative; no cache look-up,
   no fuzzy scan, so an install/remove entering through a root can never be attributed to another
   ship's stale refit cache. Root cause of the "Phaeon leak" observed during the revision era.
2. **`rootCarriesModule(root, member)`** (FleetMemberUtils.kt:435) — validates the refit-root
   candidate actually carries the entering module by `hullVariantId` STRING equality (root id or
   `stationModules.values`), failing closed on null variants/ids. The refit branch ONLY returns a
   root that both matches the stable id AND carries the module; otherwise null => ZERO whole-ship
   work. Never cross-ship.
3. **`ShipModifications.shouldAllowInstallation(member, exotic)`** (Extensions.kt:1035) —
   `underExoticLimit || alreadyHasExotic`. Wired into the handler install gates
   (HullmodExoticHandler.kt:777, :904). This removed the original "install vetoed at limit" block
   that kept a root from ever receiving the exotic's hullmod. Not in any revision.
4. **`onPostDestroy` + `clearHullmodLeftovers`** (HullmodExotic.kt:260-397). `onPostDestroy` is
   genuinely new — it did not exist at the rev-16-era baseline (812a109), and nothing in revisions
   1-18 called for a destroy-time cleanup pass. It runs AFTER the handler flows/sequence complete:
   - re-removes exotic bookkeeping for both `member` and `rootMember`,
   - `finishUninstallSequenceForMember(rootMember)`,

     `removeEffectsBeforeShipCreation` across the union of (a) callback `variant`'s module
     variants, (b) `member.variant`'s module variants, (c) `getWholeVariantGraph(member)`,
     (d) `getWholeVariantGraph(rootMember)`.
   This belt-and-braces pass is what made OP reset deterministic on every module for the refit
   and planetside paths (`TEST_RESULTS20`-`22`). It was largely delivered/committed by the user

## Clarifying Implementation Details

- **Why the resolver looks the way it does.** The bleed problem was never "find the root"; it
  was "you attributed a write to the WRONG root". The committed resolver therefore refuses to
  guess: a named member IS the root; a child on the refit screen must match the stable cached
  root id AND be carried by that root's variant strings; everywhere else it returns `member` so
  the planet-side path never touches `RefitButtonAdder` (whose cache holds "the last ship
  refitted", not "this ship" — the exact trap that caused the Phaeton leak).
- **String, not identity.** All attribution in `rootCarriesModule` and the resolver is by
  `hullVariantId`/`id` strings. `===` on variants is never used for ownership: variants reshuffle
  across `fixVariant` churn and refit cloning.
- **`clearHullmodLeftovers` is intentionally redundant.** The Handler flows + `onPostDestroy`
  already remove bookkeeping on the recorded `listOfVariantsWeInstalledOn`; the cleanup pass is a
  no-cost second sweep over the union of graphs (remove-first, then stats scrubbing) precisely so
  a regenerated/display clone or a child member the flows never visited cannot keep reduced OP.
  `removeEffectsBeforeShipCreation` is idempotent (single `removeListenerOfClass` in
  AlphaSubcoreHM/DaemonCoreHM; `hullSize` is currently ignored), so double-scrubbing is safe.
- **`shouldAllowInstallation` is the root-install fix.** Without it, a root module at exotic
  limit (e.g. after InstallMethod's direct write) was vetoed; the installing child got the hullmod
  but the root never did. The committed gate lets the already-present exotic through so the whole
  ship gets covered.
- **No `updateStats()` inside the install/remove write-through anywhere** — the rev-5
  StackOverflowError rule survived the consolidation; the only refresh points are
  `ExoticaTechHM.addToFleetMember` and the refit flow's own triggers.
- **Test artifacts** `TEST_RESULTS20`.txt through `TEST_RESULTS22`.txt capture acceptance;
  `TEST_RESULTS22` is the authoritative pass for both refit and planetside ExoticaTech.

## Reflection

This plan is the record of a genuinely hard problem whose hard part was never code volume — it
was **attribution**: deciding, unambiguously and in every screen, which ship a write belongs to
when identical hulls make string-only matching ambiguous and object identity churns with every
refit. The revision ladder documents the theorem: instance identity fails inside the refit;
fuzzy string scans fail across twins; a cached root fails when stale. The committed solution
does not resolve ownership more cleverly — it *refuses to guess*. Named member => that member.
Refit child => only the exact cached root that demonstrably carries it. Everything else does
zero whole-ship work. Adding a deterministic `onPostDestroy` cleanup on top then closed the
second half of the problem (OP reset) without re-opening the first. The enduring lessons:
favor fail-closed over smart resolution, keep string keys over instance identity, and let a
consolidation pass (rev-16) delete machinery rather than extend it.
