# plan-orchestration.txt — why plan-cache-revised2 and plan-fix-hullmod-installation run together

Umbrella doc, drafted Aug 3 2026. Coordinates the two implementation plans:
- plan-fix-hullmod-installation.txt  (campaign/refit: root hullmod persistence)
- plan-cache-revised2.txt            (combat: child data resolution, Phases 2b + 3)

## The shared root cause chain (one system, two visible symptoms)
Exoticatech ships are multi-object systems: a ROOT FleetMemberAPI + child module FMAPIs whose data
lives in per-variant tags. Every layer (refit highlight, campaign advance, combat stats) depends on
the hullmod being present on the ROOT AND on the whole-ship data being readable. Two distinct bugs bite:

1. HULLMOD STRIPPING (plan-fix-hullmod-installation)
   - addToFleetMember decides from the member's OWN mods only (ExoticaTechHM.java:86), and
     generateForFleetMember never returns null (ShipModFactory.kt:25-40), so the REMOVE branch fires
     whenever the member's own upgrades/exotics are empty — even if a child module owns the exotic.
   - advanceInCampaign strips the hullmod on `mods == null` (ExoticaTechHM.java:283-287). The ROOT's own
     variant carries no tags (data lives on the children) -> root loses the hullmod during campaign.
   - Consequence: refit highlight gone, campaign effects dead, AND in combat the root hullmod is absent
     -> applyEffectsBeforeShipCreation never fires on the root -> moduleMap never populated
     (ExoticaTechHM.java:511-519) -> child stats cannot resolve to root.

2. COMBAT TAG LOSS (plan-cache-revised2)
   - Engine renames REFIT child variants `_Start` -> `_0`/`_1` and the combat clones drop their tags
     (proven in plan-cache-revised2, "NEW EVIDENCE"). ShipModLoader.get() then returns null for those
     children -> thousands of NULLs -> child-owned exotics/upgrades never apply in combat.
   - Fix lives in VariantTagProvider (campaign-anchored recovery) + FleetMemberUtils helpers. The
     hullmod fix does NOT cure this; Path B is still required.

## Why both at the same time
- Complementary, not competing: fix #1 anchors the hullmod + enables moduleMap + campaign/refit;
  fix #2 recovers child DATA in combat. Fixing only one leaves the other symptom fully visible.
- They contaminate each other's diagnostics: the combat child NULLs (#2) include cascade noise from the
  missing root hullmod (#1). Fixing #1 first gives plan-cache's Phase 2b probe a clean baseline that
  measures the TRUE remaining gap (engine tag loss only).
- Independent code surfaces: hullmod work touches ExoticaTechHM.java + ShipModLoader.kt; cache work
  touches VariantTagProvider.kt + FleetMemberUtils.kt. No overlap -> low merge risk.

## Execution order (approved)
1. plan-fix-hullmod-installation (this run):
   a. ShipModLoader.getWholeShipMods + consolidateHullmod
   b. ExoticaTechHM.addToFleetMember (hoisted root resolution + consolidate gate + full-tree strip)
   c. ExoticaTechHM.advanceInCampaign (whole-ship-aware null path, root-anchored effects)
2. Validate on Windows (plan-fix-hullmod-installation.txt "Validation").
3. Then plan-cache-revised2 Phase 2b probe (fresh logs) -> Phase 3 Path B implementation.

## FleetMemberHierarchy verdict
- getRootVariant / getAllModules / getFleetContext / isOwnerOf = identity WeakHashMap + `===` -> BROKEN
  after fixVariant churn (documented FleetMemberHierarchy.kt:19-40, 145-166, 253-273). NOT a blocker for
  either plan; both route around it.
- findRootVariantId = stable string keys (FleetMemberHierarchy.kt:181-193) -> the ONLY hierarchy call
  allowed, and only as an aid in getWholeShipMods for leaf->root climbing.
- A FleetMemberHierarchy refactor is optional tech debt; postpone until a feature actually needs it.

## Design constraints carried by both plans
- No identity-based FleetMemberHierarchy calls in new code.
- Whole-ship data = variant-tree walk (stationModules recursion), the proven fallback already in
  ShipModLoader.getAllDataFromStatsAPI (ShipModLoader.kt:105-126).
- Dedupe whole-ship reads by hullVariantId (stock/REFIT/combat clones share the id; iterating both
  would double-fire campaign effects).
- Keep VariantTagProvider.kt CRLF; incremental builds on Windows; never wipe pre-fix logs.
