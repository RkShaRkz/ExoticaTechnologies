1. CORRECTED MECHANISM (why the re-pour happens)
-----------------------------------------------------------------------
Full call graph of onInstall (exhaustive): the only automatic callers are
  ExoticaTechHM.applyEffectsBeforeShipCreation:596 -> HullmodExotic.applyExoticToStats:283
  ExoticaTechHM.applyEffectsAfterShipCreation:683  -> HullmodExotic.applyToShip:293
Both are gated by shouldSkipModification, which does `if (!presentSomewhereOnShip) skip = true`
(ExoticaTechHM:415), presentSomewhereOnShip being computed from ShipModLoader.getWholeShipMods
(:569-577). There is NO other re-applier: installThisHullmodExoticToFleetMembersVariant (the
only re-putExotic + writeThrough) is only called from onInstall's flow callbacks. The ExoticaTechHM
"self-heal" (isActuallyEmpty -> removeHullmodEverywhere, :554) only strips the HULLMOD, never
re-adds exotics, so it is NOT the re-pour.

=> A FULLY evicted exotic cannot re-fire. Therefore the re-pour PROVES the eviction/read is
   incomplete: the presence-read still sees an exotics-bearing ShipModifications on some node
   after the strip, so the storm faithfully re-fires and the LENIENT no-data branch merely
   PERMITS the repaint (remove deleted the bookkeeping, so shouldInstall seeds+returns true).
   The no-data branch is the enabler, NOT the driver.

2. RETRACTION of the "record the clones in installData" theory (do NOT implement that)
-----------------------------------------------------------------------
- VariantTagProvider.set:164-171 -> writeThrough:202-235 already mirrors EVERY write onto all
  object graphs a later read can walk (member.variant, resolved root, checkRefitVariant, refit
  display tree), fuzzy-matching the node per graph (findVariantInTree:242-258). So a strip on one
  recorded variant already propagates base-only to every graph - the tag is graph-synchronized
  BY CONSTRUCTION.
- invalidateVariantAcrossAll:339-361 purges the ENTIRE fuzzy id-family (left_Start/left_0/...) from
  EVERY member's cache on every write, so the read cache (get:91-147) cannot serve a stale sibling
  on the normal path.
=> Stripping "clones" from HullmodExotic's callbacks is unnecessary (writeThrough already mirrors)
   and would split the gatekeeping responsibility the user wants kept in HullmodExoticHandler.
   Recording clone instances in installData would not change real strip coverage. NOT doing that.

3. NARROWED SUSPECTS (to be separated by the rev-18 diagnostics)
-----------------------------------------------------------------------
(S1) Stale cache shadowing a stripped tag: VariantTagProvider.get:118-133 serves a cached
     exotics-bearing value (exact or fuzzy id-family) for a variant whose TAG no longer has
     exotics / has no tag, because that graph variantId was never re-cached after the strip.
     (invalidateVariantAcrossAll only purges; it does not re-seed the new base-only value for
     every mirrored graph id, and writeThrough adds TAGS to graph nodes but does NOT write cache
     entries for those graph ids.)
(S2) Write/read root-instance mismatch: the strip's mirror target is
     findShipScopedRootVariant(member, variant) (FleetMemberUtils:286 - instance/ownership aware,
     :292 treeInstanceContains, :302), while the presence-read's root is
     getWholeShipModsData:103 -> resolveRootVariant:119 -> findRootVariantByHullId:332 (FIRST match
     by hullVariantId across the fleet, no instance/ownership check, ambiguous for two identical
     hulls). If the strip mirrors onto tree A but the read walks twin tree B, B's nodes keep the
     exotic -> present stays true.
(S3) refit-root vs true-root installData key fragmentation (installs recorded under a refit-root
     key are not covered by a later planet-side true-root remove). Lower likelihood, noted only.

4. WHAT rev-18 ADDS (diagnostic only - zero behavior change)
-----------------------------------------------------------------------
(a) ShipModLoader.getWholeShipModsData -> logWholeShipModsDiag (read side, WHERE):
    transition-gated (fires on gain / change / clear, not every frame). One line per transition:
      getWholeShipModsData() DIAG member.id=N
        root=<hullVariantId>@<identityHashCode> refit=<...>
        nodes=[<hullVariantId>@<identityHashCode>:[exoticKeys], ...]
    This is the presence decision's own view: it shows the resolved root INSTANCE the read used
    and exactly which node still reports an exotic, so (S2) and the retained node are pinned
    directly. Compare the root @identityHashCode against the existing write-side
    VariantTagProvider.writeThrough "ANCHOR resolvedRootGraph=..." ERROR line for the same member.
    A "nodes=[] NO_EXOTICS_ANYWHERE" line marks the full clear; a following re-appearance marks
    the re-pour.

(b) VariantTagProvider.get -> logStaleCacheShadow (read side, WHY - confirms/refutes S1):
    log-ONCE, fires ONLY in the real bug: a cache-served value HAS exotics while the variant's
    actual TAG has none (or no tag). Logs served vs tag exotic keys and EXACT/FUZZY source.
      get() DIAG STALE_CACHE_SHADOW member.id=... variant=<id>@<hash> source=EXACT|FUZZY(..)
        servedExotics=[...] tagExotics=[...|NO_TAG]

(c) The write side is ALREADY instrumented: VariantTagProvider.writeThrough logs ANCHOR (member,
    variant, resolvedRootGraph) and ANCHOR-TARGET (graph -> target node, tag) at ERROR. These
    show exactly what the strip wrote and to which nodes/roots, for comparison against (a)/(b).
