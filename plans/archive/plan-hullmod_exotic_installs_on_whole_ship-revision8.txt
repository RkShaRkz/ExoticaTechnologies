WHY REVISION 7 LEFT STALE OP (investigation)
--------------------------------------------
The overslaught is a multi-module ship, and BOTH twins carry identical module hull variant ids:
'Start' and 'Standard' both reduce to 'tbj_overslaught' once the last _suffix is stripped
(fuzzyVariantMatch, ExoticaTechHM.java:48-61 / fuzzyVariantIdEquals, FleetMemberUtils.kt:256-260),
so the two roots' station modules SHARE every module id.

The module->root fast path, FleetMemberUtils.moduleMap (FleetMemberUtils.kt:18), is a global
HashMap<hullVariantId, FleetMemberAPI>. It is cleared and repopulated on EVERY modular root's
applyEffectsBeforeShipCreation (ExoticaTechHM.java:528-536) and consulted FIRST by
findMemberForStats before identity-based resolution. With two twins, whichever root's stats pass
ran LAST writes the shared module ids, so a module's statsForOpCosts can resolve to the OTHER
twin's root member. The removal listener then scrubs the wrong ship's stats; the module that
initiated the uninstall keeps its OP cut. Rev-7 scrubbed both stats objects per variant but still
resolved WHICH member armed/scrubbed via the same wrong fast path for the very stats subset that
no identity-carrier can disambiguate (synthetic statsForOpCosts from propagateFromVariantTree have
no entity and no fleetMember).

FIX - FLEETMEMBERUTILS SOLE-OWNER GUARD (plan A; option B - multimap - deferred)
--------------------------------------------------------------------------------
The moduleMap stays the fast path ONLY while it is trustworthy. A new per-id owner registry makes
that decidable:

- add private moduleOwnerIds: MutableMap<String, MutableSet<String>> tracking which member ids
  have registered each module hullVariantId since the last clear.
- add @JvmStatic clearModuleMap() (clears map AND registry) and
  @JvmStatic registerModuleOwner(moduleVariantId, member) (last-writer-wins map entry + owner
  registry add). All write sites move to these helpers.
- add private isSoleModuleOwner(moduleVariantId) == (owner set size == 1).
- findMemberForStats order: identity-carriers FIRST (stats.entity as ShipAPI parentStation climb ->
  findMemberFromShip/fleetMember), then stats.fleetMember, then moduleMap[id] ONLY when
  isSoleModuleOwner(id), else the existing activeFleets + searchFleetForStats loop (which
  disambiguates by statsForOpCosts === stats object identity - NOT variant identity; no '==='
  variant comparisons anywhere).
- findMemberFromShip no longer consults moduleMap at all (parentStation climb, fleetMember, then
  findMemberForStats).
- findFleetForVariant guards its moduleMap hit with isSoleModuleOwner.
- MRU write-back of slow-loop results into moduleMap was considered and REJECTED (user choice):
  in the twin case the id stays non-sole regardless, so a write-back can never make collision reads
  fast; the map self-heats on every modular-root stats pass anyway.
