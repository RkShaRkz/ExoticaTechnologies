# plan-fleet_member_hierarchy_removal.txt — Remove FleetMemberHierarchy dead machinery, keep the string-map subsystem

## 1. Objective
Slim `FleetMemberHierarchy` down to the only members that are actually used by the
rest of the codebase, deleting the dead identity-based machinery and the broken
`ShipModLoader` fallback loop that referenced it. The object is **kept in place**
(reduced standalone object), its 5 used methods are kept **verbatim** (a move, not
a rewrite), and call sites are left untouched.

## 2. Model (validated against source)
Only **5 members** have external callers (12 call sites). They form a fully
self-contained string-map subsystem reading only `variantIdToParentId`:

| Member | Calls |
|---|---|
| `findRootVariantId(String)` | ExoticaTechHM:73, :271; ShipModLoader:128, :132 |
| `isChildStats(stats)` | ExoticaTechHM:382 |
| `refreshFleetCache(v)` | ExoticaTechHM:108-109 |
| `reinitialize()` | ETModPlugin:67, :95 |
| `getAllModules(stats)` | ShipModLoader:82 (loop being deleted) |

Everything else (~12 identity-based/dead members + the `variantToParent`
WeakHashMap) has **zero external callers** and is deleted with the slim.

`findRootVariantId` (:181-193) and `isChildStats` (:138-141) are self-contained:
they read only `variantIdToParentId` and call no other FleetMemberHierarchy member.
So the string-map subsystem relocates cleanly with nothing else attached.

### 3.2 Replace `ShipModLoader.getAllDataFromStatsAPI` fallback loop (:82-88)
Removes the last reference to a deleted member (`FleetMemberHierarchy.getAllModules`).

**Regression discovered in testing (do NOT simply delete):** the `getAllModules(stats)`
loop was NOT a redundant fallback — it was the only reader of the ROOT FM's own
`ShipModifications`. Its replacement, `collectModuleMods(rootFM, rootFM.variant, ...)`,
walks only `stationModules` children and never reads the root's own mods. Deleting the
loop outright made `getAllForStats`-fed paths (`applyEffectsAfterShipCreation:619`,
`applyEffectsToFighterSpawnedByShip:703`, `advanceInCombat:424` in ExoticaTechHM.java)
miss root-owned exotics, so the after-creation highlight (`applyToShip`) never fired on
any module while `applyEffectsBeforeShipCreation`'s `getWholeShipMods` (which DOES
include the root) still applied the stats. A/B test isolated the regression to this
exact hunk (FleetMemberHierarchy kept-members are semantically identical).

**Fix (applied):** collect the root FM's own mods explicitly before the child walk:

```kotlin
val rootFM = FleetMemberUtils.findMemberForStats(stats) ?: return allModsList.toList()
get(rootFM, rootFM.variant)?.let { allModsList.add(it) }
collectModuleMods(rootFM, rootFM.variant, allModsList)
```

This preserves the original read semantics (root + children) and also fixes the
single-module-ship case (`stationModules` empty previously returned `[]`). No identity
machinery is re-introduced.

### 3.3 The one behavioral change (explicit)
In relocated `mapVariantTree`, the identity write `variantToParent[child] = parent`
is dropped because the map is being deleted. Nothing a call site reads changes:
`findRootVariantId`/`isChildStats`/`getCacheSize` read only `variantIdToParentId`,
which is still populated and refreshed identically.

### 3.5 Logging hygiene (logspam.txt — verified root cause)
The `logspam.txt` file shows a per-frame ERROR flood from FleetMemberHierarchy during combat
against enemy modular ships (HIVER burrower/deathfly/aphid/queen, hullVariantIds `18ba18c_*`):

- Source: `getFleetContext()`'s `logError("Fleet context missing for member: ...")`
  (old FleetMemberHierarchy.kt:292). Enemy child-module members never resolve into
  `CampaignEventListener.activeFleets`, so it logged every poll; the old doc comment already
  called it a benign consequence of variant instance churn.
- `getFleetContext` is in the DELETE set, and none of the 5 kept methods call it (verified:
  the identity-based members that did — `isRootModule`/`isChildModule`/`getRootModule`/
  `getAllModules` — have zero external callers; `getAllModules(stats)` survived only at
  ShipModLoader:82, deleted in 3.2). The spam class is **removed**, not silenced.
- The retained `reinitialize()` `logError` guard fires at most once per game load and only
  when `Global.getSector()` is null; the INFO enter/exit traces in `refreshAllCaches`/
  `refreshCache` are dropped entirely (user decision) so the slimmed object emits **zero**
  log output in normal play.

### 3.4 No other call-site changes
`findRootVariantId` (ExoticaTechHM:73, :271; ShipModLoader:128, :132),
`isChildStats` (ExoticaTechHM:382), `refreshFleetCache` (ExoticaTechHM:108-109),
`reinitialize` (ETModPlugin:67, :95) all keep targeting the unchanged kept methods.
No signatures change, no rewiring.
