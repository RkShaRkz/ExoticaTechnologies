ISSUE #39 HULLMOD EXOTICS -> "INSTALL ON WHOLE SHIP" — REVISION 3
================================================================
Root anchor is now the correct ship even with two identical multimodule hulls.

Revision 3 changes ONLY THE RESOLUTION in FleetMemberUtils.findRootVariantMember. The
keeper changes from rev 1 (HullmodExotic.kt member = rootMember, :99) and the
single-file scope stay exactly the same.

WHY REVISION 2 FAILED
---------------------
Rev 2 anchored on RefitButtonAdder.member while runningFromRefitScreen(), but that member is
the TRANSIENT CHILD FMAPI while a module is being edited (per user verification + the
getRefitDisplayVariant KDoc at RefitButtonAdder.kt:471-483), so the rev-2 guard's
refitRoot.variant.stationModules.isNotEmpty() check bailed for the very two-ship case it was
built for, and the flow silently fell into the original first-match fuzzy scan, which is a
coin flip between identical hulls.

CORE INSIGHT (applies to every revision)
----------------------------------------
findRootVariant / findRootVariantByHullId / ModuleVariantHierarchy all KEY THE MODULE ID
STRINGS: root.variant.hullVariantId -> child ids. Two copies of the same hull produce
byte-identical child hullVariantId strings, so any string-keyed scan resolves to whatever
copy the fleet iteration happens to visit first. No amount of PID-prefix stripping or deeper
string matching helps; the strings are literally the same.

THE ONLY UNIQUE SIGNAL IS INSTANCE IDENTITY
-------------------------------------------
findRootVariantMember is always called with the CONCRETE FAM/FMAPI that entered the flow
(from hullmod hullmod-installed events, refit dialogs, campaign processing). The tree of the
true owner instance-contains that member.variant object (===). The sibling identical ship's
tree holds DIFFERENT variant instances, so it cannot win. This fixes the two-copy tie.

ALGORITHM (ownership-first, all-candidates, 4-step)
---------------------------------------------------
1) if member.variant.stationModules.isNotEmpty() -> member          (it is a root)
2) targetId = member.variant.hullVariantId
   candidates = ALL root FMs (own fleet then active fleets, no early return)
               whose stationModules tree fuzzy-contains targetId
3) resolve:
   1-OWNER   candidates.first { treeInstanceContains(it.variant, member.variant) }   the ONLY
             disambiguating step: the true owner, unique across identical hulls.
   2-REFIT   runningFromRefitScreen() && RefitButtonAdder.member is one of the candidates -> it.
             Identity comparison only, no extra scan; NO-OP while editing a module, because
             then RefitButtonAdder.member is the transient child, which never matches a root
             candidate. Deliberate narrowness: cannot pick a sibling.
   3-FIRST   candidates.firstOrNull() (status quo for the single-ship case)
   4-FALLBACK findRootVariant(member, member.variant) -> findModuleMember(root) ?: member
             (old behavior preserved as the last resort)

NEW HELPERS (private, FleetMemberUtils)
---------------------------------------
matchingRootMembers(member, childId): List<FleetMemberAPI>  LinkedHashSet<>, own fleet first
   then activeFleets; keeps every fuzzy match (NO first-match short-circuit so step 3 can see
   the full candidate set).
treeInstanceContains(root, child): Boolean  root.forEachModuleVariant { node === child }.
   Resolves identity against the CONCRETE variant graph that the tree actually holds (the KDoc
   on ShipVariantAPI.forEachModuleVariant at Extensions.kt:983-990 documents the walker visits
   descendant leaves, so a root is by construction not == its own child).

DIAGNOSTICS (WARN-level, added because FleetMemberUtils previously had no logger)
--------------------------------------------------------------------------------
findRootVariantMember logs at WARN on entry: member toString + member.id, isChild
(= shipName.isNullOrEmpty(), the same heuristic HullmodExotic.kt:69 used before rev 2),
targetId, runningFromRefitScreen(), RefitButtonAdder.member (+ id), and the full candidate id
list; then logs which step resolved and to which root id. These are NOT production spam (one
line per whole-ship flow per member) and are the definitive in-game diagnostic: if step 1
never fires, refit cloning is replacing tree children and the instance test is defeated — the
parked name/identity comparison becomes the fix.

-------------------------------------------
