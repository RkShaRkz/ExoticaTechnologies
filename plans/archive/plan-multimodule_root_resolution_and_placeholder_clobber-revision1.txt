## 1. Intent
Installing a Modification (e.g. FullMetalSalvo) on a CHILD module of a multi-module ship
(e.g. ork_superdread_main_standard) must apply to the WHOLE ship and the exoticatech hullmod must
persist across refit. Today it applies to the child only and the module loses the hullmod on
return to refit. Two independent defects are suspected to cause this; this plan instruments the
code to prove which fires, then fixes it.

## 5. Current defect analysis (re-verified against HEAD 78ee74e)

### Defect 1 — content-less (bandwidth-only) writes clobber content tags
- ShipModFactory.generateForFleetMember (ShipModFactory.kt:26-39) and the market overload
  (:43-58) build a bandwidth-only ShipModifications and persist it with ShipModLoader.set
  (:37 / :55) when get(member, member.variant) is null. generateForChildModules (:85-96)
  persists a per-child placeholder at :93.
- VariantTagProvider.set (VariantTagProvider.kt:147) always does removeFromTags(variant) +
  addTag (:157-160) then writeThrough (:169). writeThrough (:200-222) fuzzy-matches EVERY object
  graph by hullVariantId and blindly removeFromTags + addTag (:215-221), so it can replace a real
  "$$EXOTICA$$" tag on the matching node of the root graph with a content-less one.
- A SECOND writer is the outer call at CustomExoticaPanel.kt:45
  (get(member, variant) ?: set(member, variant, generateForFleetMember(member))): even if the
  factory stops writing, this outer set re-writes the empty mods.
- NOT YET ISOLATED: generateForChildModules, InstallMethod, and HullmodExotic's uninstall also
  set with variant != member.variant. The panel as the sole culprit is unproven.

### Defect 2 — root resolution returns null on the first child install
- ExoticaTechHM.addToFleetMember (ExoticaTechHM.java:55) uses
  ModuleVariantHierarchy.findRootVariantId, which reads variantIdToParentId — populated only by
  mapVariantTree / refreshFleetCache. It is refreshed ONLY in the APPLY branch
  (ExoticaTechHM.java:90-91), i.e. AFTER the decision — so on the first child install it is cold.
- ShipModLoader.resolveRootVariant:121 has the SAME map dependency: a getWholeShipMods call with a
  CHILD variant walks only the child while the map is cold.

## 7. Log signals to look for (Phase 0 -> Phase 1 diagnosis)
Defect 1 (clobber):
- `VTP.set ... mods=` EMPTY where an earlier `SML.collectWholeShipMods` shows the same node held
  content; or `VTP.set TAG-ADDED ... tags=1` immediately followed by a decode of emptiness on a
  previously-full node.
- Which member/variant triggered it (CustomExoticaPanel vs generateForChildModules vs uninstall).
Defect 2 (cold root):
- `ET.addToFleetMember ... rootVariantId=null` on the first child install.
- `SML.resolveRootVariant ... NO-HIERARCHY-ROOT -> self` when passed a CHILD variant.
- `FMU.resolveWholeShipRootMember ... -> self` for a child module (unnamed member outside refit).

## 8. PROPOSED fixes (retained; to be confirmed/refined by Phase 0 logs)
Fix 1 (approved option (a)) — non-destructive placeholder writes:
- ShipModFactory: before persisting a placeholder, resolve the root
  (FleetMemberUtils.resolveWholeShipRootMember, fall back to member) and read the whole ship; only
  persist when no entry satisfies shouldApplyHullmod().
- CustomExoticaPanel.kt:45: drop the outer set -> `get(...) ?: generateForFleetMember(...)`.
- OPEN (user objection): the panel-clobber hypothesis must be validated with a log BEFORE removing
  the outer set. Phase 0 supplies that evidence.
Fix 2 — robust root resolution in addToFleetMember:
- Primary FleetMemberUtils.resolveWholeShipRootMember; guard on `resolved != member`; hierarchy
  fallback; keep a boolean child-display gate.
- OPEN (user objection): the base plan's `refreshAllCaches()` fallback walks every active fleet per
  call (perf), and the `resolved != member` guard sends every non-refit call to the fallback
  (e.g. CampaignEventListener.kt:491, DerelictsEFScript.java:112). Phase 0 logs should tell us how
  often the fallback actually fires before any cache walk is added.
