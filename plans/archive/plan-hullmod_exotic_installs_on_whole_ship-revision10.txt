## 2. Root cause
1. `checkRefitVariant()` returns `RefitButtonAdder.variant` only when `RefitButtonAdder.member == this`, else `this.variant` (RefitButtonAdder.kt:490-495). While a child is edited, the root's call collapses to the campaign root → evidence 1.6(b)/(c).
2. `writeThrough` mirrors only `member.variant` + resolved root + `member.checkRefitVariant()`; it **never adds `getRefitDisplayVariant()`** (VariantTagProvider.kt:207-219). So the edited ship's live display tree is not re-tagged/applied by root-anchored whole-ship writes.
3. Strip side **is** display-aware (`removeHullmodEverywhere` strips `getRefitDisplayVariant()`, ExoticaTechHM.java:243-246) — the install/tag side has no counterpart. Every "works only after Refit→Cargo→Refit" = the display tree being re-derived from the (correct) campaign tree on screen switch.
4. Duplication (4 AlphaSubcores, step 14): clones proliferate via `fixVariant` (ExoticaTechHM.java:105); reads don't dedupe.
5. Identical-root twins can't be told apart by hullVariantId strings — only FleetMember id can.

## 3. Design (lean, single-shot)
**Principle:** authoritative writes live on the campaign tree; campaign + refit + **display** graphs are treated symmetrically on install **and** remove; display-tree inclusion is attributed O(1) from refit state (no fleet scan, no fuzzy matching, identical-hull-safe); reads dedupe.

### 3.1 Display-tree gate (replaces Fix 1's string gate — and the reachability idea)
- refit closed ⇒ `getRefitDisplayVariant()==null` and `getRootMember()==null` are cleared together (RefitButtonAdder.kt:80-89) ⇒ gate no-ops, zero work.
- refit active ⇒ include the display tree iff `getRootMember()?.id == actorRootId`, where `actorRootId = actor.id` when `actor.shipName != null`, else `getRootMember()?.id` (transient child of the refit ship).
- Applied identically in `getWholeVariantGraph` step 3 **and** in `writeThrough` mirrors.
- Why not the membership/hullId-scan idea: a display clone is itself a non-member fake object, so "not a fleet member's variant ⇒ include" would wrongly include ship B's display tree when walking ship A — the exact pre-Fix cross-ship vector. Refit state attributes possession in O(1) with zero compares against other ships.

### 3.2 Symmetric hullmod/listener + stats refresh (covers the OP read path without a diagnostic run)
On install **and** remove, after tag writes, apply/scrub the exotica hullmod and refresh `statsForOpCosts` across campaign + refit + display graphs — mirroring what remove already does (dual-scrub of `parentFleetMember.stats` + `variant.statsForOpCosts`, HullmodExoticHandler.kt:374-390). This covers every candidate OP read object (display clone / campaign node / stale stats) regardless of which one the refit bar binds to — no extra diagnostic run needed. Also covers the root member's own stats. Implemented as `HullmodExotic.refreshStatsEffectsAcrossShipGraphs(rootMember, apply=…)`, called from `onInstall` (apply=true) and `onDestroy` (apply=false); each graph node is gated on `hasHullMod` before apply/scrub so skipped-install modules are never costed. Idempotent: `AlphaSubcoreHM`/`DaemonCoreHM` guard their listener add, others use fixed-id modifyFlat or BaseHullMod no-ops.

> Explicitly NOT in scope: extending the `exoticatech` HULLMOD onto the display tree (an earlier draft added `installHullmodRecursive(getRefitDisplayVariant())` in `ExoticaTechHM.addToFleetMember`). Reverted as over-extension: `exoticatech` is `affectsOPCosts() == false`, the actual OP reducer `et_alphasubcore`+tags already reach the display tree via `getWholeVariantGraph` step 3, and the exoticatech hullmod on the display tree is already delivered by `fixVariant` clone inheritance + the existing backstops (ExoticaTechHM.java:113-131). The hullmod thing was fixed long ago; this plan touches only the tag/OP economy.

### 3.3 Read dedupe
`addPostDescriptionSection`, the exotics UI, and `getWholeShipMods` key on `(member.id, hullVariantId)` — composite `"memberId:hullVariantId"` key in `ShipModLoader.collectWholeShipMods` scopes the walk so identical-root twins can never dedupe into each other's mods; kills the 4-copy duplication.
