# plan-hullmod_exotic_installs_on_whole_ship.txt

## 1. Objective
`shouldShareEffectToOtherModules(...)` currently drives **two different concerns**:

1. **Install extent** — *which modules get the exotic's hullmod installed on*
   (`HullmodExotic.onInstall`/`onDestroy`, `HullmodExoticHandler` install flows).
2. **Effect sharing** — *whether an exotic owned by one module applies exotic-level
   effects to other modules* (`ExoticaTechHM.shouldSkipModification`, at the
   `Modification`/`Exotic` level).

This plan splits them. A new `installsOnWholeShip()` on `HullmodExotic` (and the
same read in `HullmodExoticHandler`) becomes the single source of truth for concern
#1. `shouldShareEffectToOtherModules(...)` stays on concern #2 only.

After this patch it becomes possible to build a `HullmodExotic` that installs its
hullmod on **one** module while still sharing exotic-level effects (e.g. a cargo /
armor buff in `applyToStats`) to **all** modules — because the two flags are no
longer coupled. (The user will author and test such an exotic themselves; this plan
delivers the capability only.)

## 3. Behavior preservation (the point)
- `AlphaSubcore` / `DaemonCore`: `installsOnWholeShip() = true` exactly reproduces
  today's whole-ship hullmod install. In `CheckAndInstallOnMemberModule` the seeding
  list (`:802` → `getInitialVariantsListForMember(member, true)` =
  `getChildModuleVariantList(member)`, plus the root variant) matches today's
  `shouldShareEffectToOtherModules = true` path; STRICT-mode `expected` list
  therefore contains every child, so each child still passes `shouldInstall`.
- Default `false`: hullmod installs on the single member only — the new capability
  for authors (combined with exotic-level sharing via `shouldShareEffectToOtherModules`).
- `Exotic.kt` NOTE (`:28-:29`), `Modification`/`Exotic` sharing paths, and
  `ExoticaTechHM.java` `shouldSkipModification` (`:331`, `:380`) are **unchanged**.

## 4. Not touched
- issue #39 / child-to-child sharing — the root-only lookup (`only root modules are
  able to share ... to child modules`) and the FIXME comment become a follow-up
  revision that can leverage the new flag + the post-rename root-resolution helpers
  (`ModuleVariantHierarchy.findRootVariantId`, `FleetMemberUtils.findRootVariant`,
  `findRootVariantByHullId`).
- No concrete proof-of-concept exotic is added (user authors the cargo/armor exotic
  during testing).
- Legacy `logspam.txt` etc. — untouched.

## 5. Validation
- `grep -rn "shouldShareEffectToOtherModules(null, null)" src/` → empty for the
  HullmodExotic install/remove paths (`HullmodExotic.kt`, `HullmodExoticHandler.kt`).
  Remaining `shouldShareEffectToOtherModules` matches are the legitimate
  exotic-level sharing reads (`AlphaSubcore`/`DaemonCore` overrides, `ExoticaTechHM`,
  other `Exotic` subclasses).
- Windows build + in-game (user-held):
  - `AlphaSubcore` unchanged: hullmod installed on every module; uninstall strips
    everywhere (symmetric).
  - `DaemonCore` unchanged: same.
  - User's experimental single-module HullmodExotic: hullmod on ONE module, shared
    buff on ALL modules.
- No automated test changes required — the handler tests use anonymous HullmodExotics
  and never touch this flag.
