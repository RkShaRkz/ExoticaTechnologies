## 1. Objective
`HullmodExotic.onInstall` / `onDestroy` (and, via them, the whole-ship install
flows) currently use whatever `FleetMemberAPI` enters them as the anchor for the
whole-ship install bookkeeping. When that member is a **child** module rather than
the ship's **root**, the whole-ship semantics silently break:

- `getChildModuleVariantList(child)` returns `[]` (`Extensions.kt:985-994`) → sibling
  modules are never discovered, so the "install on all modules" step is skipped.
- `HullmodExoticKey(hullmodExotic, parentFleetMemberId)` (`HullmodExoticHandler.kt:876`)
  anchors the handler's `lookupMap` `InstallData` on the *child* member's id. A later
  removal that enters from the root (shop / refit destroy, `removeHullmodExoticFromFleetMember`)
  looks up by the root id → key mismatch → nothing is cleaned up.
- `isUnderExoticLimit`, the `shipName == null` sanity check, `getCorrectMods`, and the
  `installThisHullmodExoticToFleetMembersVariant` / `unapplyExoticHullmodAndRemoveExoticaAndHullmod`
  callbacks are all keyed off the entry member.

This is the "other part" of the decoupling plan and resolves the FIXME at
`HullmodExotic.kt:70-72` / the related comments at `:74-78` and `:121-126`
(issue #39: "only root modules are able to share effects to all other (child) modules").

This is reachable in-game today: `ALLOW_INTERACTION_OUTSIDE_EXOTICA_OR_REFIT = true`
(`HullmodExoticHandler.kt:25`) means the flows run in STRICT mode even off-screen —
e.g. the `applyExoticToStats → onInstall(member)` ship-creation path processes every
module's stats and feeds child members into whole-ship flows.

The fix: **anchor whole-ship installs on the ship's root member**, resolving it from
whatever member enters `onInstall` / `onDestroy`. Child entries then converge on the
same root-anchored key the root entries use.

## 2. Change set

### 2.1 `FleetMemberUtils.kt`
Add one small helper that reuses the existing root-resolution machinery (no new
matching logic):

- `findRootVariant(member, member.variant)` (`FleetMemberUtils.kt:213`) already
  returns the variant directly when it owns station modules (the root), otherwise
  scans the member's variant tree then the fleet for the owning tree (fuzzy id match,
  refit/combat-clone safe), and falls back to `variant` itself for single-module
  ships / unreachable trees.
- `findModuleMember(rootVariant)` (`FleetMemberUtils.kt:194`) maps the root variant
  back to its `FleetMemberAPI`, falling back to null when unreachable (e.g. cold
  `statsForOpCosts`).

```kotlin
/**
 * Resolves the root [FleetMemberAPI] of the module tree containing [member], used by
 * whole-ship (`installsOnWholeShip()`) install/remove flows so that bookkeeping always
 * anchors on the ship's root member regardless of which member entered the flow.
 * Returns [member] itself for single-module ships or when the root member cannot be
 * reached, preserving today's behavior in those cases.
 */
@JvmStatic
fun findRootVariantMember(member: FleetMemberAPI): FleetMemberAPI {
    val rootVariant = findRootVariant(member, member.variant)
    if (rootVariant == member.variant) return member
    return findModuleMember(rootVariant) ?: member
}
```

## 3. Behavior preservation (the point)
- `installsOnWholeShip() == false`: `rootMember` is never computed; `member` flows
  through exactly as today — zero change.
- Single-module ships and root entries: `findRootVariant(member, member.variant)`
  returns `member.variant` → `rootMember == member` → identical to today.
- Child entries: flows now behave as if the root entered — children discovered,
  one root-anchored `InstallData` key per ship, symmetric removal.
- Handler internals (`shouldInstallHullmodExoticToVariant` / `install...ToVariant` /
  `shouldRemove...FromVariant` / `remove...FromVariant`, STRICT vs LENIENT,
  `getInitialVariantsListForMember`, `getChildModuleVariantList`) are **unchanged**:
  they already document and assume the root-module contract, which this change now
  satisfies at the single chokepoint (`HullmodExotic`).

## 4. Not touched
