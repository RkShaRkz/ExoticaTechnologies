# plan-hullmod_installation.txt — root hullmod must persist while ANY module has ANY Modification

Drafted: Aug 3 2026. NOT yet implemented. Sibling of plan-variant_cache-revision2.txt (no supersession).

## Objective (user spec, verbatim intent)
- Installing an Exotica on a CHILD module MUST add the hullmod (`ExoticaTechHM`, `HULLMOD_ID`) to the ROOT variant.
- The root's hullmod MUST NOT be removed as long as ANY module of the ship has ANY `ShipModifications`
  installed — not just `Exotic` subclasses but `Upgrade` subclasses too (i.e. any `Modification` subclass).
- `addToFleetMember` must decide from the WHOLE ship's ShipMods, not just its own:
  `consolidateHullmod(mods, wholeShipMods): Boolean`.
- Non-root (child-module) FMAPI behavior stays exactly as-is.
- When the ENTIRE ship is empty of modifications, the hullmod must be removed from everywhere
  (resolves the TODO at ExoticaTechHM.java:546).

## Root cause
1. `addToFleetMember` (ExoticaTechHM.java:66-162) gates on `mods.shouldApplyHullmod()` (line 86) where
   `mods = ShipModFactory.generateForFleetMember(member)` (line 69) — the MEMBER'S OWN mods only.
   `generateForFleetMember` NEVER returns null (ShipModFactory.kt:25-40 generates bandwidth + persists),
   so the else (REMOVE) branch at line 151 fires whenever the member's own upgrades/exotics are empty —
   EVEN IF a child module owns the exotic. Refitting the root with exotics only on a child → root stripped.
2. `advanceInCampaign` (ExoticaTechHM.java:275-300) reads own mods via `ShipModLoader.get` (line 276) and on
   `mods == null` unconditionally `removePermaMod(HULLMOD_ID)` (line 284) + return. The root's own variant
   carries no exotic tags (data lives on the child variant) → `mods == null` → root loses the hullmod.
   THIS is the observed "left refit, flew around, came back → root had no hullmod" bug.
3. Why child-install works TODAY: `addToFleetMember(childFM)` → child's own mods non-empty → APPLY branch →
   `installHullmodRecursive(root)` (lines 100-101) + `propagateFromVariantTree` (line 106) → whole tree gets HM.
   The fix must keep this path intact.
4. Log evidence (temp4.log.txt): `NULL mods => removed HM` lines (86-87, 147-148, 212-213, 227-228) — members
   `tbj_overslaught_left_0` / `tbj_overslaught_left_Start`, HM stripped when own mods null; FullMetalSalvo
   `APPLYING` on all 3 modules (96-128) only because the ROOT still held the hullmod at that combat (strip
   happens later in campaign).

## FleetMemberHierarchy verdict (the "is it broken" question)
- `getAllModules` / `getAllChildModules` / `findRootVariant` / `getFleetContext` / `isOwnerOf` are IDENTITY-based
  (`WeakHashMap<ShipVariantAPI, ShipVariantAPI>` + `===` scans). These BREAK after `fixVariant` churn (REFIT
  clones not yet registered) — documented in FleetMemberHierarchy.kt:19-40, 145-166, 253-273. DO NOT use them.
- `findRootVariantId` (FleetMemberHierarchy.kt:181-193) uses `variantIdToParentId` = STABLE string keys
  (child hullVariantId → parent hullVariantId). Safe across fixVariant. This is the ONE hierarchy method
  usable, and only as an aid.
- PREFERRED: compute whole-ship mods by WALKING THE VARIANT TREE (`variant.getStationModules()` +
  `getModuleVariant(slot)`), the exact pattern already proven as the fallback in
  `ShipModLoader.getAllDataFromStatsAPI` (ShipModLoader.kt:105-126) — added precisely because the FM
  hierarchy collapses children to rootFM. Child data lives in child VARIANT TAGS (VariantTagProvider is the
  only writing provider, `setOnlyIfFirst()` → i==0), so `ShipModLoader.get(rootMember, childV)` reads them.

## Design
### 1. `ShipModLoader.getWholeShipMods(member, variant): List<ShipModifications>`  (new @JvmStatic)
- Include member's own `get(member, variant)` + recursive stationModules walk (extract/reuse `collectModuleMods`).
- Union over `member.getVariant()` AND `checkRefitVariant(member)` trees (both carry tags; APPLY installs on both).
- If the passed variant has no stationModules (leaf/child), resolve the root FIRST:
    - `FleetMemberHierarchy.findRootVariantId(variant.hullVariantId) != null` → find root member via
      `findMemberByVariantId` pattern → walk the ROOT's tree.
    - else treat the passed variant as root.
- No identity-based hierarchy calls. Allocation-free per-frame: this is a refit/campaign event, not a combat loop.

### 2. `consolidateHullmod(mods, wholeShipMods): Boolean`  (user's API)
    mods?.shouldApplyHullmod() == true || wholeShipMods.any { it.shouldApplyHullmod() }
- `shouldApplyHullmod` (ShipModifications.kt:62-64) already covers `upgrades.hasUpgrades() ||
  exotics.hasAnyExotic()` = ANY `Modification` subclass.

### 3. `addToFleetMember` (ExoticaTechHM.java:66) — root-aware decision
- Hoist root resolution UP (lines 90-97 already do `findRootVariantId` + `findMemberByVariantId`).
- Compute `wholeShipMods = ShipModLoader.getWholeShipMods(rootMember, rootMember.getVariant())`.
- Gate: `if (consolidateHullmod(mods, wholeShipMods))` → existing APPLY branch UNCHANGED.
- else (WHOLE SHIP EMPTY) → strip the ENTIRE tree: `removeFromFleetMember(rootMember)` + strip the root's
  `checkRefitVariant` tree (resolves TODO :546). Replaces the current member-only removal (151-161).
- Child uninstall that empties the ship → rootMember stripped too. Child uninstall while ANOTHER module still
  has mods → consolidate true → APPLY, no strip.

### 4. `advanceInCampaign` (ExoticaTechHM.java:275) — no more blind strip
- `mods == null` → `wholeShipMods = ShipModLoader.getWholeShipMods(member, member.getVariant())`
    - empty → `removePermaMod` + return (unchanged behavior when ship truly clean).
    - non-empty → KEEP hullmod; iterate wholeShipMods for upgrade/exotic `advanceInCampaign` effects
      (solves ShipModFactory.kt:81-89 TODO — campaign effects now fire for child-owned exotics).
- `mods != null` → existing loop UNCHANGED (skip whole-ship computation — zero added per-frame cost).
